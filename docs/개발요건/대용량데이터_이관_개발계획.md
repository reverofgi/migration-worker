# Sybase IQ 16.0 → 16.2 대용량 데이터 이관 Pure Java Worker 개발 Master Prompt

## 0. 작업 지시

당신은 **Sybase IQ, Java/JDBC, MyBatis, 대용량 데이터 이관, 배치 시스템 및 데이터 검증**에 전문성을 가진 Senior Java/DBA Engineer이다.

이 문서는 2026-09-28 현재 `migration-worker` 저장소에 구현된 소스를 기준으로 정리한 개발·운영 기준서다. 아래 요구사항과 실제 프로젝트 파일을 **구현의 기준(Source of Truth)**으로 사용한다.

```text
현재 구현 기준
├── CLI 및 3개 DB Connection 초기화
├── TASK_ID 단위 이관 대상 1건 조회
├── Sybase IQ Native Extract
├── MIG_EXEC_DTL 단계별 시작/완료/오류 이력
├── AS-IS 집계 및 MIG_VRF_RESULT 저장
├── Sybase IQ LOAD TABLE
├── 적재 성공 후 DAT/BIN 파일 정리
├── TO-BE 집계 및 AS-IS/TO-BE 비교
└── MIG_VRF_RESULT TGT_* 및 VRF_STAT_CD 저장
```

임의의 DB 컬럼, 테이블, 설정값, SQL 문법, 메타데이터를 만들어내지 않는다.

요구사항이 충돌하거나 DB 구조가 확인되지 않는 경우:

1. 충돌 내용을 식별한다.
2. 현재 구현, 확정 요구사항, 미구현 사항을 분리한다.
3. `docs/Table정보/*.sql`과 실제 DB Metadata를 우선한다.
4. 확인할 수 없는 부분은 TODO 또는 Extension Point로 남긴다.

# 1. 시스템 목적

HP-UX 환경의 Sybase IQ 16.0 AS-IS 데이터를 Linux 환경의 Sybase IQ 16.2 TO-BE로 이관한다.

```text
대상 테이블 : 약 13,000개
전체 데이터 : 약 250TB
공유 볼륨   : 약 50TB
```

GODIS 웹 배치 프레임워크와 Migration Worker는 TO-BE 시스템의 Linux/Docker 환경에서 실행된다. AS-IS와 TO-BE가 함께 접근하는 공유 볼륨을 데이터 전달 매체로 사용한다.

```text
AS-IS Sybase IQ 16.0
      │ Native Extract / BFILE
      ▼
Shared Volume (50TB)
      │ LOAD TABLE
      ▼
TO-BE Sybase IQ 16.2
```

Java는 원본 행이나 LOB 전체를 Heap으로 운반하지 않는다. Java의 역할은 Metadata 조회, SQL 생성, Native 명령 실행, 파일 관리, 검증값 산출 및 결과 저장을 조정하는 Orchestrator다.

# 2. 실행 구조
## 2.1 배치 실행 구조
```text
GODIS Web Batch Framework (TO-BE Linux / Docker)
   │ Shell: EXEC_ORD, TASK_ID, MNGR_ID
   ▼
MigrationWorkerApplication
   ├── GODIS/MariaDB Connection
   ├── AS-IS Sybase IQ 16.0 Connection
   └── TO-BE Sybase IQ 16.2 Connection
            │
            ▼
       MigrationWorker
            │
            └── TASK_ID가 지정한 TABLE_ID + PROC_ORD 1건 순차 처리
```

현재 구현에서 하나의 `TASK_ID`는 `MIG_TBL_INFO`의 이관 단위 1건을 식별해야 한다.

```text
이관 단위 = TABLE_OWNER + TABLE_ID + PROC_ORD
```

`selectMigrationTable()`은 단일 `MigrationTableInfo`를 반환하므로 하나의 `TASK_ID`에 여러 행이 매핑되면 MyBatis 단건 조회 오류가 발생한다. 여러 분할 또는 여러 테이블은 GODIS가 서로 다른 `TASK_ID` 실행으로 조정한다.

Worker 내부 Thread Pool은 사용하지 않는다.


## 2.2 공유볼륨 및 개발PC의 저장소 위치

### 2.2.1 저장소 구성 목적
Sybase IQ Native Extract와 LOAD TABLE은 데이터베이스 서버에서 실행되므로 Linux 서버의 로컬 경로를 사용한다.
반면 Java Migration Worker가 추출 파일을 확인하거나 삭제할 때는 Worker가 실행되는 운영체제에서 접근할 수 있는 경로를 사용한다.
따라서 다음 두 경로는 표기 방식만 다를 뿐, 반드시 동일한 물리 파일을 가리켜야 한다.

| 구분 | 접근 주체 | 경로 형식 |
|---|---|---|
| `DB_EXPORT_*` | Sybase IQ DB Engine | Linux 로컬 경로 |
| `WORKER_EXPORT_*` | Java Migration Worker | Windows 로컬 경로 또는 UNC 경로 |
```
Sybase IQ DB Engine
/opt/sap/iq161/IQ-16_1/demo/data
/opt/sap/iq161/IQ-16_1/demo/blob
              │
              │ 동일한 물리 저장소
              ▼
Java Migration Worker
\\192.168.0.122\migration-data\data
\\192.168.0.122\migration-data\blob
```

### 2.2.2 Linux 서버의 저장소
Sybase IQ가 설치된 Linux 서버 정보:
```
서버 주소: 192.168.0.122
```
Sybase IQ가 추출 및 적재 SQL에서 사용하는 서버 경로는 다음과 같다.
```
# 일반 데이터 파일(.dat) 저장 위치
DB_EXPORT_DATA_PATH=/opt/sap/iq161/IQ-16_1/demo/data

# LOB 파일(.bin) 저장 위치
DB_EXPORT_BLOB_PATH=/opt/sap/iq161/IQ-16_1/demo/blob
```

각 설정의 용도는 다음과 같다.

| 설정 | 용도 |
|---|---|
| `DB_EXPORT_DATA_PATH` | Sybase IQ Native Extract가 생성하는 일반 데이터 파일 저장 경로 |
| `DB_EXPORT_BLOB_PATH` | BLOB 등 LOB 컬럼의 바이너리 파일 저장 경로 |

이 경로는 Java 프로세스의 경로가 아니라 Sybase IQ 데이터베이스 서버가 인식하는 Linux 경로다.

### 2.2.3 Samba 공유 설정
Windows 개발 PC에서 추출 파일에 접근할 수 있도록 Linux 서버에 Samba가 구성되어 있다.
권장 공유 구조는 다음과 같다.
```
[migration-data]
path = /opt/sap/iq161/IQ-16_1/demo
```
이 구조라면 Windows에서 다음과 같이 접근한다.
```
일반 데이터: \\192.168.0.122\migration-data\data
LOB 데이터 : \\192.168.0.122\migration-data\blob
```
실제 Samba 설정에서 migration-data가 /opt/sap/iq161/IQ-16_1/demo/blob에 직접 매핑되어 있다면 data 디렉터리에는 접근할 수 없다.
개발 전에 Linux 서버의 smb.conf에서 migration-data의 실제 path를 반드시 확인한다.

### 2.2.4 Windows 개발 PC에서 공유 폴더 연결
Windows 탐색기 주소 표시줄에 다음 경로를 입력한다.
```
\\192.168.0.122\migration-data
```
인증 창이 나타나면 Samba 계정으로 로그인한다.
```
사용자 이름: sybase
비밀번호: 별도 전달된 Samba 계정 비밀번호
```

연결 후 다음 경로에 접근할 수 있는지 확인한다.
```
\\192.168.0.122\migration-data\data
\\192.168.0.122\migration-data\blob
```
읽기뿐만 아니라 Java Worker가 적재 완료 후 파일을 삭제해야 하므로 생성·조회·삭제 권한을 모두 확인해야 한다.

### 2.2.5 Java Migration Worker 경로
Java Worker가 파일에 접근할 때 사용하는 경로다.
UNC 경로를 직접 사용하는 경우:
```
WORKER_EXPORT_DATA_PATH=\\192.168.0.122\migration-data\data
WORKER_EXPORT_BLOB_PATH=\\192.168.0.122\migration-data\blob
```
개발 PC에서 공유 폴더를 C:\migrationTemp에 연결한 경우:
```
WORKER_EXPORT_DATA_PATH=C:/migrationTemp/data
WORKER_EXPORT_BLOB_PATH=C:/migrationTemp/blob
```

각 설정의 용도는 다음과 같다.

| 설정 | 용도 |
|---|---|
| `WORKER_EXPORT_DATA_PATH` | Java Worker가 `.dat` 파일을 조회하고 삭제하는 경로 |
| `WORKER_EXPORT_BLOB_PATH` | Java Worker가 LOB `.bin` 파일과 LOB 디렉터리를 조회하고 삭제하는 경로 |

단순히 Windows 탐색기에서 공유 폴더에 접속하는 것만으로는 C:\migrationTemp 경로가 자동 생성되지 않는다.
C:\migrationTemp 방식을 사용하려면 해당 경로가 Samba 공유 폴더와 실제로 연결되어 있어야 한다.
연결하지 않았다면 UNC 경로를 직접 설정해야 한다.

### 2.2.6 경로 대응 관계
Samba 공유 루트가 /opt/sap/iq161/IQ-16_1/demo인 경우의 경로 대응 관계는 다음과 같다.

| 파일 유형 | DB Engine 경로 | Windows Worker 경로 |
|---|---|---|
| 일반 데이터 | `/opt/sap/iq161/IQ-16_1/demo/data` | `\\192.168.0.122\migration-data\data` |
| LOB 데이터 | `/opt/sap/iq161/IQ-16_1/demo/blob` | `\\192.168.0.122\migration-data\blob` |

예를 들어 다음 두 파일은 동일한 물리 파일이어야 한다.
```
DB Engine:
  /opt/sap/iq161/IQ-16_1/demo/data/DWDB_TB_LOB_007_10_data.dat

Java Worker:
  \\192.168.0.122\migration-data\data\DWDB_TB_LOB_007_10_data.dat
```

LOB 디렉터리 역시 동일하게 대응되어야 한다.
```
DB Engine:
  /opt/sap/iq161/IQ-16_1/demo/blob/DWDB_TB_LOB_007_10

Java Worker:
  \\192.168.0.122\migration-data\blob\DWDB_TB_LOB_007_10
```

### 2.2.7 개발 전 확인사항
개발자는 배치 실행 전에 다음 항목을 확인한다.
1. Samba의 migration-data 공유 루트가 실제로 어느 Linux 경로인지 확인한다.
2. data와 blob 디렉터리 모두 Windows에서 접근 가능한지 확인한다.
3. DB 경로와 Worker 경로가 동일한 물리 파일을 가리키는지 확인한다.
4. Worker 계정에 파일 조회 및 삭제 권한이 있는지 확인한다.
5. C:/migrationTemp를 사용할 경우 Samba 공유와 실제로 연결되어 있는지 확인한다.
6. Windows 서비스나 배치 계정으로 실행할 경우에도 Samba 인증이 유지되는지 확인한다.
7. 운영 환경에서는 Windows 개발 경로가 아니라 Docker에 마운트된 Linux Worker 경로를 별도로 설정한다.

# 6. 중요: Metadata와 Physical Schema를 구분한다

## 6.1 Migration Metadata Schema

GODIS MariaDB에 존재한다.

```text
GPCL_CM_CD_VAL
MIG_TBL_INFO
MIG_COL_INFO
MIG_VRF_RESULT
MIG_EXEC_DTL
```

## 6.2 Physical Table Schema

실제로 이관하는 Sybase IQ 테이블이다.

```text
AS-IS : TABLE_OWNER.TABLE_NM
TO-BE : TGT_DB_PREFIX.TABLE_NM
```

현재 Extract는 원천 `TABLE_OWNER`를 사용하고, Load와 TO-BE Verify는 `TGT_DB_PREFIX`를 대상 owner/schema로 사용한다.

`MIG_COL_INFO`는 전체 컬럼명, 순번, 타입, PK/NULL 여부와 검증 플래그를 제공한다. 현재 `SybaseIQSchemaReader`는 이 Metadata로 `TableSchema`를 구성하며 Sybase Catalog/JDBC `DatabaseMetaData`를 조회하지 않는다.

# 7. MIG_TBL_INFO

## 목적

`TASK_ID`를 기준으로 현재 실행의 테이블, 분할순서, 접속 PREFIX 및 이관 정책을 조회한다.

주요 컬럼:

| 컬럼 | 의미 | 현재 사용처 |
| --- | --- | --- |
| `TABLE_OWNER` | AS-IS 테이블 owner | Extract, 검증 키, 작업 디렉터리 |
| `TABLE_ID` | 논리 테이블 ID | `MIG_COL_INFO` 조인, 파일명, 결과 키 |
| `PROC_ORD` | 분할/처리 순서 | 파일명, 결과 키, 조건 단위 |
| `TASK_ID` | GODIS 실행 작업 ID | CLI 조회 키 |
| `SRC_DB_PREFIX` | 원천 접속 설정 PREFIX | AS-IS Connection 생성 |
| `TGT_DB_PREFIX` | 대상 접속 설정 PREFIX 및 현재 대상 owner | TO-BE Connection/SQL |
| `MIG_LOAD_MODE` | `T` Truncate, `A` Append | Load 정책 |
| `LOB_YN` | LOB 보유 여부 | Metadata와 컬럼 타입 일치 검증 |
| `TABLE_NM` | 실제 물리 테이블명 | Extract/Load/Verify |
| `MIG_COND` | WHERE 본문 | AS-IS/TO-BE 동일 조건 집계 |
| `MNGR_ID` | 담당자 | 결과 저장 |

조회 SQL의 핵심은 다음과 같다.

```sql
FROM MIG_TBL_INFO
WHERE TASK_ID = #{taskId}
ORDER BY TABLE_OWNER, TABLE_ID, PROC_ORD
```

현재 구현 제약:

```text
TASK_ID당 결과는 정확히 1건이어야 한다.
USE_YN='Y' 조건은 현재 조회 SQL에 포함되어 있지 않다.
```

# 8. MIG_TBL_INFO 샘플 실행 단위

현재 대표 검증 대상은 다음 구조다.

```text
TABLE_OWNER  = DWDB
TABLE_ID     = TB_LOB_007
PROC_ORD     = 10
SRC_DB_PREFIX= DWDB
TGT_DB_PREFIX= MIGTGT
MIG_LOAD_MODE= T
LOB_YN       = Y
TABLE_NM     = TB_LOB_007
```

물리 테이블:

```text
AS-IS : DWDB.TB_LOB_007
TO-BE : MIGTGT.TB_LOB_007
```

파일 작업 단위:

```text
디렉터리 : DWDB_TB_LOB_007_10
DAT      : TB_LOB_007_10_data.dat
BIN      : TB_LOB_007_10_<PK>_<COL_NM>.bin
```

# 9. MIG_TBL_INFO Schema 주의사항

기본키는 다음과 같다.

```text
TABLE_OWNER + TABLE_ID + PROC_ORD
```

`PROC_ORD`는 단순 표시 순서가 아니라 동일 테이블을 서로 다른 `MIG_COND`로 나눈 이관 단위를 식별한다.

`MIG_LOAD_MODE='T'`는 대상 테이블을 먼저 비우므로, 동일 대상 테이블을 여러 `PROC_ORD`로 나눌 때 모든 실행에 `T`를 사용하면 앞서 적재한 데이터가 삭제된다. 일반적으로 최초 구간만 `T`, 후속 구간은 `A`로 Metadata를 설계해야 한다.

`TGT_DB_PREFIX`는 접속 Property PREFIX인 동시에 현재 SQL에서 TO-BE owner로 사용된다. 두 의미가 다른 환경에서는 별도 Metadata 컬럼 도입을 검토해야 한다.

# 10. MIG_COL_INFO

목적:

```text
전체 컬럼 구조
+ PK/NULL 속성
+ 컬럼별 검증 함수 설정
```

주요 컬럼:

```text
TABLE_OWNER, TABLE_ID, COL_ID, COL_ORD, COL_NM, DATA_TYPE
PK_YN, NULL_YN
SUM_YN, MIN_YN, MAX_YN, AVG_YN
HASH_YN, DIST_CNT_YN, NULL_CNT_YN
```

`YnBooleanTypeHandler`가 `Y/N`을 Java boolean으로 변환한다.

검증 대상은 다음 중 하나 이상이 `Y`인 컬럼이다.

```text
SUM_YN OR MIN_YN OR MAX_YN OR AVG_YN
OR HASH_YN OR DIST_CNT_YN OR NULL_CNT_YN
```

`HASH_YN`은 대상 선택에는 포함되지만 FNV-1a SQL이 아직 구현되지 않았으므로 `Y`이면 `ValidationException`으로 중단한다.

# 11. MIG_COL_INFO 샘플

`TB_LOB_007`의 기본키는 다음과 같다.

```text
COL_ORD=1, COL_ID=SEQ_NO, DATA_TYPE=BIGINT, PK_YN=Y
```

Metadata 생성 SQL 원칙:

```text
DECIMAL/NUMERIC       → TYPE(precision, scale)
CHAR/VARCHAR/BINARY   → TYPE(width)
BIGINT/INTEGER/...    → TYPE만 저장
DATE/TIME/TIMESTAMP   → TYPE만 저장
```

정수형에 `(10,0)` 같은 표현을 붙이지 않는 이유는 Sybase IQ 정수형이 DECIMAL의 precision/scale 문법을 사용하지 않으며, Java 추출 문자열 길이 규칙이 기본 타입별로 고정되어 있기 때문이다.

# 12. Validation Target 및 컬럼 정렬

조회와 Worker 양쪽에서 `COL_ORD` 오름차순을 보장한다.

```sql
ORDER BY TABLE_OWNER, TABLE_ID, COL_ORD
```

Worker는 다음을 추가 검증한다.

```text
TABLE_OWNER/TABLE_ID 일치
COL_ORD > 0
COL_ORD 중복 금지
COL_NM 중복 금지
COL_NM SQL identifier 검증
DATA_TYPE 공백 금지
```

Extract의 행 순서는 `PK_YN='Y'` 컬럼을 `COL_ORD` 순서로 정렬한 다음 아래처럼 생성한다.

```sql
ORDER BY PK_COL_1, PK_COL_2, ...
```

PK가 없으면 일반 테이블은 `ORDER BY` 없이 추출한다. LOB/BFILE 테이블은 파일명 생성에 PK가 필요하므로 PK가 없으면 Extract를 중단한다.

# 13. BLOB/CLOB 처리

현재 Extract의 file-backed 대상 타입:

```text
BLOB, LONG BINARY, VARBINARY, BINARY, IMAGE
CLOB, LONG VARCHAR, LONG NVARCHAR, TEXT
```

파일명은 PK 값과 컬럼명을 조합한다.

```text
<blob-root>/<TABLE_ID>_<PROC_ORD>_<PK...>_<COL_NM>.bin
```

NULL LOB은 `NULL_TOKEN`, BFILE 실패는 `BFILE_ERROR_TOKEN`으로 DAT 파일에 기록한다.

Load 매핑:

```text
CLOB/LONG VARCHAR/LONG NVARCHAR/TEXT → ASCII FILE
BLOB/LONG BINARY/IMAGE               → BINARY FILE
```

현재 제한:

```text
VARBINARY/BINARY의 FILE 방식 LOAD TABLE은 명시적으로 지원하지 않는다.
```

`MIG_TBL_INFO.LOB_YN`과 실제 file-backed 컬럼 존재 여부가 다르면 Extract를 중단한다.

# 22. Pipeline

현재 Application과 `MigrationWorker.execute()`의 실제 순서:

```text
Step 0  Application: MIG_TBL_INFO/PREFIX/Property 조회 → TASK 로그 설정 → Connection 생성
Step 0-1 Worker: 전달받은 Metadata 및 3개 Connection 검증
Step 1  UNLOAD 시작 저장 → unload(table) → UNLOAD 완료 저장
Step 2  UNLOAD_VRF 시작 저장 → unloadResultVerify(table) → UNLOAD_VRF 완료 저장
Step 3  LOAD 시작 저장 → load(table) → LOAD 완료 저장
Step 4  LOAD_VRF 시작 저장 → loadResultVerify(table) → LOAD_VRF 완료 저장
Step 5  정상 종료
```

각 단계 시작 전 `MIG_EXEC_DTL.STRT_DTM`과 `EXEC_STAT_CD='10'`을 저장한다. 단계가
정상 반환되면 `END_DTM`과 `EXEC_STAT_CD='20'`을 저장하며, 예외가 발생하면
`END_DTM`과 `EXEC_STAT_CD='30'`을 저장한 후 원래 예외를 다시 전달한다.

세부 흐름:

```text
AS-IS Native Extract
 → AS-IS 집계 및 SRC_* 저장
 → TO-BE LOAD/COMMIT
 → DAT/BIN 즉시 정리
 → TO-BE 집계
 → SRC/TGT 비교
 → TGT_* 및 VRF_STAT_CD 저장
```

파일은 이전 사용자 확정 정책에 따라 Load 커밋 직후 삭제되며 TO-BE Verify 불일치 시에도 복구용 파일은 남지 않는다.

구현 클래스:


```sql

SET TEMPORARY OPTION TEMP_EXTRACT_BINARY = 'OFF';
SET TEMPORARY OPTION TEMP_EXTRACT_NULL_AS_EMPTY = 'OFF';
SET TEMPORARY OPTION TEMP_EXTRACT_NULL_AS_ZERO = 'OFF';

SET TEMPORARY OPTION TEMP_EXTRACT_ROW_DELIMITER = '<actual row delimiter>';
```

```sql
SELECT <COL_ORD 순서 표현식>
  FROM TABLE_OWNER.TABLE_NM
 WHERE <MIG_COND>
```

완료 또는 실패 후 `TEMP_EXTRACT_NAME1=''`, `TEMP_EXTRACT_BINARY='OFF'`로 정리한다.

Nullable 비문자 타입은 NULL token과 CASE 반환 타입을 맞추기 위해 `VARCHAR(n)`으로 변환한다. 정수형, DECIMAL, 실수형, 날짜/시간형마다 안전 길이를 별도로 계산한다.

# 24. Step 2 AS-IS Verification

구현 클래스:

```text
UnloadResultVerifyWorker
```

검증 대상은 7개 플래그 중 하나 이상이 `Y`인 `MIG_COL_INFO` 컬럼이다.

동적 집계:

```sql
SELECT COUNT(*) AS ROW_COUNT,
       SUM(...), MIN(...), MAX(...), AVG(...),
       COUNT(DISTINCT ...),
       COUNT(*) - COUNT(...)
  FROM TABLE_OWNER.TABLE_NM
 WHERE <MIG_COND>
```

저장 순서:

```text
1. 집계 성공
2. 동일 EXE_ORD/TABLE_OWNER/TABLE_ID/PROC_ORD 기존 결과 DELETE
3. SRC_* INSERT
4. COMMIT
```

INSERT 실패 시 DELETE도 rollback한다. 검증 대상이 0개이면 기존 결과만 삭제한다.

# 25. Validation Function과 Data Type

지원 함수:

```text
COUNT(*), SUM, MIN, MAX, AVG, COUNT(DISTINCT), NULL COUNT
```

Metadata 설정이 실제 Sybase IQ 타입에 유효한지는 DB 실행 결과로 검증한다. 현재 Worker는 잘못 설정된 `SUM(VARCHAR)` 등을 사전에 완전 판별하지 않으며 DB 오류를 `ValidationException`으로 전달한다.

현재 HASH 정책:

```text
HASH_YN=Y → 검증 대상에는 포함
          → HASH SQL 미정의로 ValidationException
SRC_HASH_VAL/TGT_HASH_VAL → NULL 저장
```

집계값은 `varchar(38)` 범위를 초과하면 저장하지 않고 검증 오류로 처리한다.

```text
AS-IS VALUE / TO-BE NULL  → MISMATCH
```

# 27. Validation 비교

구현 클래스:

```text
ValidationResultComparator
```

비교 항목:

```text
ROW_COUNT
SUM
MIN
MAX
AVG
DIST_CNT
NULL_CNT
```

정책:

```text
COUNT/SUM/AVG/DIST_CNT/NULL_CNT → BigDecimal.compareTo()
숫자형 MIN/MAX                 → BigDecimal.compareTo()
문자·날짜형 MIN/MAX            → 문자열 값 비교
```

따라서 `1.0`과 `1.00`은 일치한다. AVG 허용오차 설정은 현재 없으므로 정확한 수치 일치를 요구한다.

컬럼별 모든 활성 검증값이 일치하면 `VRF_STAT_CD='10'`, 하나라도 다르면 `'20'`이다.

중요 정책:

```text
검증 불일치는 예외나 exit code 5를 발생시키지 않는다.
TGT_*와 VRF_STAT_CD='20'을 저장하고 WARN 로그 후 배치를 정상 종료한다.
```

# 29. 분할 처리

현재 `SPLIT_YN` 컬럼은 사용하지 않는다. 분할은 다음 Metadata 조합으로 표현한다.

```text

+ 서로 다른 PROC_ORD
+ 서로 다른 MIG_COND
```

GODIS는 동일 대상 테이블의 실행 순서와 `MIG_LOAD_MODE(T/A)`를 책임진다.

# 30. 파일 삭제

확정 정책:

```text
LOAD TABLE 성공
 → TO-BE commit
 → 현재 TABLE_ID/PROC_ORD DAT 삭제
 → 현재 TABLE_ID/PROC_ORD 접두사의 BIN 삭제
 → 빈 작업 디렉터리 삭제 시도
```

LOAD 실패 시 파일을 삭제하지 않는다.

삭제 범위:

```text
DAT: <TABLE_ID>_<PROC_ORD>_data.dat 정확히 1개
BIN: <TABLE_ID>_<PROC_ORD>_*.bin
```

Windows/SMB에서는 열거 중 삭제 시 파일이 건너뛰어질 수 있으므로, 일치 BIN 파일이 없는 순회가 나올 때까지 반복한다. 파일 목록 전체를 Heap에 적재하지 않는다.

빈 디렉터리 삭제에서 `DirectoryNotEmptyException`이 발생하면 다른 파일을 보존하고 정상 처리한다. 실제 대상 파일 삭제 실패는 Load 후 cleanup 실패로 기록하고 exit code `4`를 반환한다. 이 시점의 TO-BE 데이터는 이미 commit되었음을 오류 메시지에 명시한다.

---

# 31. Batch Group 실패 정책

현재 실행은 이관 단위 1건이므로 단계 예외가 발생하면 즉시 종료한다.

```text
Extract 오류         → exit 3
Load/cleanup 오류    → exit 4
Validation 처리 오류 → exit 6
Schema 오류          → exit 7
Metadata 오류        → exit 8
기타 오류            → exit 9
```

검증값 불일치는 실패 예외가 아니다. `VRF_STAT_CD='20'`으로 관리한다.

단계 실행 예외는 해당 `MIG_EXEC_DTL` 행을 `EXEC_STAT_CD='30'`으로 갱신한다.
오류 이력 갱신도 실패하면 이력 오류를 원래 예외의 suppressed exception으로
보존하므로 최초 업무 오류의 exit code는 바뀌지 않는다.

Retry, continue-on-error, 재연결 정책은 현재 구현되어 있지 않다.

---

# 32. 상태 관리

단계 실행 상태는 `MIG_EXEC_DTL`, 데이터 검증 상태는 `MIG_VRF_RESULT`에서 관리한다.

`MIG_EXEC_DTL` 기본키:

```text
EXE_ORD + TABLE_OWNER + TABLE_ID + PROC_ORD + JOB_TP_CD
```

`JOB_TP_CD` 값:

```text
UNLOAD
UNLOAD_VRF
LOAD
LOAD_VRF
```

단계 상태 전이:

```text
단계 시작 → STRT_DTM=NOW, END_DTM=NULL, EXEC_STAT_CD=10
정상 완료 → END_DTM=NOW, EXEC_STAT_CD=20
처리 오류 → END_DTM=NOW, EXEC_STAT_CD=30
```

동일 기본키로 재실행하면 `ON DUPLICATE KEY UPDATE`로 시작일시와 상태를 다시
초기화한다. 따라서 이 테이블은 동일 실행차수 안에서 여러 시도의 누적 이력이 아니라
단계별 최종 실행 상태를 보관한다.

현재 확정된 오류 공통코드가 없으므로 `ERR_CD`는 `NULL`로 유지한다. Worker에서
단계별 처리 건수를 반환하지 않으므로 `TOTAL_CNT`도 현재는 `NULL`이다.

`TASK_ID` 컬럼은 `MIG_EXEC_DTL`에 없으며, `MIG_TBL_INFO`에서 조회된
`TABLE_OWNER/TABLE_ID/PROC_ORD`를 통해 해당 TASK 실행 단위를 식별한다.

검증 상태:

```text
SRC 저장 직후 → VRF_STAT_CD=30
TO-BE 일치    → VRF_STAT_CD=10
TO-BE 불일치  → VRF_STAT_CD=20
CONF_STAT_CD  → 저장/갱신 시 10
```

`MIG_EXEC_DTL.EXEC_STAT_CD`와 `MIG_VRF_RESULT.VRF_STAT_CD`는 의미가 다르다.
예를 들어 AS-IS/TO-BE 값이 불일치해도 `LOAD_VRF` 작업 자체가 정상 수행되었다면
실행상태는 `20(완료)`, 해당 검증 결과는 `20(불일치)`이다.

# 33. Transaction

각 DB Transaction은 독립적이다.

```text
GODIS MariaDB Transaction
≠ AS-IS Sybase IQ Transaction
≠ TO-BE Sybase IQ Transaction
```

현재 경계:

```text
TO-BE Load               → commit/rollback
AS-IS 결과 DELETE+INSERT → 동일 GODIS transaction
TO-BE 결과 upsert        → GODIS transaction
```

분산 트랜잭션은 사용하지 않는다.

# 34. JDBC Resource Lifecycle

```text

Statement  → Native SQL 작업 단위
SqlSession → Metadata/집계 작업 단위
```

Connection은 `MigrationWorkerApplication`의 중첩 `try-with-resources`가 TO-BE/AS-IS/GODIS 순으로 닫는다.

# 44. Logging

SLF4J + Logback console appender와 `SiftingAppender`를 함께 사용한다.

테이블 Metadata 조회 후 MDC에 실행 식별자를 설정하여 TASK 실행별 로그 파일을
생성한다. 로그 디렉터리는 `GPCL_CM_CD_VAL`에서 읽은 필수 공통 Property
`WORKER_BATCH_LOG_PATH`를 사용한다.

```properties
WORKER_BATCH_LOG_PATH=C:/migrationTemp/logs
```

설정 경로가 없으면 Worker가 디렉터리를 생성한다. 경로가 파일시스템 루트이거나
디렉터리를 생성·기록할 수 없으면 Metadata 오류로 실행을 중단한다.

Samba/UNC Symbolic Link에서는 `Files.isWritable()`이 SID 기반 ACL 조회로 실제 쓰기
가능 여부와 다른 결과를 반환할 수 있으므로 사용하지 않는다. 로그 디렉터리에 작은
임시파일을 실제 생성·삭제하여 Java 프로세스의 생성 및 삭제 권한을 검증한다.

`MigrationWorkerApplication`이 `MIG_TBL_INFO`를 먼저 조회하고 공통 Property를
초기화한 직후 최종 TASK 로그 파일명을 설정한다. 이후 AS-IS/TO-BE 연결 초기화부터
Worker 종료까지 동일한 TASK 로그 파일을 사용하며 공통 `migration-worker.log`는
생성하지 않는다.

TASK Metadata 또는 공통 Property를 읽기 전에 발생한 인자·GODIS 연결·Metadata 조회
오류는 최종 파일명이나 저장 경로를 확정할 수 없으므로 콘솔에만 기록한다.

파일명 규칙:

```text
{EXE_ORD}_{TABLE_OWNER}_{TABLE_ID}_{PROC_ORD}_{yyyyMMdd_HHmmss_SSS}.log
```

예시:

```text
1_DWDB_TB_LOB_007_10_20260928_143005_123.log
```

요구사항의 `*` 구분자는 Windows 파일명에 사용할 수 없으므로 Windows 개발 PC와
Linux 운영 환경에서 동일하게 사용할 수 있는 `_`로 치환한다.

주요 로그:

```text
Worker 시작: EXEC_ORD, TASK_ID, MNGR_ID
Extract 시작/완료: table, dataFile
Load truncate/시작/완료: target table
Cleanup 완료: table, procOrd, files, bytes
검증 저장: tableId, procOrd, columns, mismatch count
불일치: colId, mismatched metrics
```

비밀번호, credential, 원본 대량 데이터는 로그에 출력하지 않는다.

# 45. Exit Code

```text
0 = SUCCESS
1 = INVALID_ARGUMENT
2 = INITIALIZATION_ERROR
3 = EXTRACT_ERROR
4 = LOAD_ERROR
5 = VALIDATION_MISMATCH (enum 예약, 현재 불일치에는 사용하지 않음)
6 = VALIDATION_ERROR
7 = SCHEMA_ERROR
8 = METADATA_ERROR
9 = SYSTEM_ERROR
```

검증 불일치는 `VRF_STAT_CD='20'`을 저장하고 exit `0`으로 정상 종료한다. 실제 검증 SQL/DB/저장 처리 실패만 exit `6`이다.

# 46. Exception 처리

모든 업무 예외는 `MigrationException`과 단계별 exit code를 보존한다.

```text
원인 SQLException/IOException
 → 단계 Exception에 cause로 연결
 → Application에서 stack trace 포함 ERROR 로그
 → exit code 반환
```

Rollback, option reset, autoCommit 복원 실패는 원 예외의 suppressed exception으로 보존한다.

```java
catch (Exception e) {
    e.printStackTrace();
}
```

같은 단순 처리는 금지한다.

# 48. 동시성

Worker 내부는 단일 main thread 순차 실행이다.

```text
한 JVM 실행 = 한 TASK_ID = 한 TABLE_ID/PROC_ORD
```

병렬성은 GODIS가 서로 다른 TASK_ID 프로세스를 실행하여 제공한다.

동일 `TABLE_ID/PROC_ORD`를 동시에 실행하면 동일 파일 경로와 결과 키를 공유하므로 외부 스케줄러가 중복 실행을 막아야 한다.

# 55. Coding Rule

## 55.1 Connection Lifecycle

```text
Application 시작
 → GODIS 연결
 → Property/PREFIX 조회
 → AS-IS 연결
 → TO-BE 연결
 → Worker 전체 처리
 → TO-BE/AS-IS/GODIS close
```

Table마다 Connection을 생성하지 않는다.

## 55.2 Connection 역할

### GODIS Connection

```text
Metadata 조회
공통 Property 조회
MIG_VRF_RESULT 저장/조회
MIG_EXEC_DTL 단계별 시작/완료/오류 저장
```

### ASIS Connection

```text
Native Extract
AS-IS Aggregate Validation
```

### TOBE Connection

```text
TRUNCATE/LOAD TABLE
TO-BE Aggregate Validation
```

## 55.3 Connection 소유권

Connection은 `MigrationWorkerApplication`이 생성·소유하고 `MigrationWorker`와 하위 Worker에 전달한다. static global Connection을 사용하지 않는다.

## 55.4 Connection Pool

독립 실행 배치이므로 사용하지 않는다.

## 55.5 Connection 장애

현재 자동 재연결/Retry는 없다. 연결 오류는 해당 단계 Exception과 exit code로 종료한다.

## 55.6 Statement Lifecycle

Native Extract, LOAD 등 작업마다 Statement를 생성하고 즉시 닫는다.

## 55.7 PreparedStatement Lifecycle

Metadata value binding은 MyBatis가 관리한다. Dynamic identifier는 검증 후 SQL에 결합한다.

# 58. 가장 중요한 설계 원칙

```text
GODIS
  │ TASK_ID
  ▼
MigrationWorkerApplication
  │ 3 Connections
  ▼
MigrationWorker
  │
  ├── AS-IS Extract
  ├── AS-IS Verify → SRC_* / status 30
  ├── TO-BE Load → commit → DAT/BIN cleanup
  └── TO-BE Verify/Compare → TGT_* / status 10 or 20
```

핵심 원칙:

> Java는 대용량 데이터를 직접 이동하지 않는다.

> 한 실행은 `TASK_ID`가 식별한 `TABLE_OWNER + TABLE_ID + PROC_ORD` 한 단위다.

> 접속정보는 `SRC_DB_PREFIX/TGT_DB_PREFIX`와 공통코드 key를 조합한다.

> `MIG_COL_INFO`는 전체 컬럼 순서, PK, NULL 및 검증 대상을 정의한다.

> Extract 행은 PK 컬럼의 `COL_ORD` 순서로 정렬한다.

> Extract와 Load는 동일한 delimiter와 NULL token을 사용한다.

> LOAD가 commit되기 전에는 DAT/BIN을 삭제하지 않는다.

> Load 성공 후에는 현재 `TABLE_ID/PROC_ORD` 파일만 스트리밍 방식으로 정리한다.

> AS-IS/TO-BE 검증 결과는 `MIG_VRF_RESULT`의 동일 실행 키에 저장한다.

> 각 이관 단계의 시작·완료·오류는 `MIG_EXEC_DTL`의 실행 키와 `JOB_TP_CD`로 관리한다.

> 숫자는 `BigDecimal`로 비교하고 NULL 정책을 명확히 적용한다.

> 불일치는 TO-BE 데이터를 보존하고 `VRF_STAT_CD='20'`만 기록한 뒤 정상 종료한다.

> 구현되지 않은 HASH, Pipeline Schema Validation, Retry 기능을 완료된 것으로 표현하지 않는다.
