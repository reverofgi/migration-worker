# 질의사항
HP-Unix의 SybaseIQ 16.0환경(이하 ASIS)에서 운영되는 ADW의 데이터를 Linux의 SybaseIQ 16.2환경(이하 TOBE)으로 이관하는 프로젝트입니다.
테이블의 갯수는 13000개, 데이터싸이즈는 250TB 이며, 동일한 네트워크환경에서 공유볼륨(50TB)를 이용해서 데이터를 이관해야 합니다.
이관할때 테이블의 특징과 데이터의 용량 등을 감안한 이관계획이 필요합니다.
이관을 위한 배치프로그램은 아래(SybaseIQServerSideOrchestrator) 같이 고려중입니다.
SybaseIQServerSideOrchestrator를 검토하고 추가의견이나 보다 좋은 방법이 있으면 추천바랍니다.

```
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.Statement;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class SybaseIQServerSideOrchestrator {

    private static final String DB_URL = "jdbc:sybase:Tds:192.168.1.100:2638?ServiceName=IQDB";
    private static final String USER = "DBA";
    private static final String PASS = "sql";

    public static void main(String[] args) {
        // 테이블 목록 (13,000개 테이블을 파티셔닝하여 스레드 풀로 처리)
        String[] tableList = getTableListFromDB(); 

        // DB 서버 CPU/Disk I/O 사양에 맞게 동시 작업 스레드 수 설정 (예: 8~16)
        int maxParallelThreads = 8;
        ExecutorService executor = Executors.newFixedThreadPool(maxParallelThreads);

        for (String tableName : tableList) {
            executor.submit(() -> {
                executeServerSideUnload(tableName);
            });
        }

        executor.shutdown();
    }

    private static void executeServerSideUnload(String tableName) {
        // Java Heap 메모리를 거의 사용하지 않음 (쿼리 트리거만 수행)
        try (Connection conn = DriverManager.getConnection(DB_URL, USER, PASS);
             Statement stmt = conn.createStatement()) {

            conn.setAutoCommit(true);

            // 1. 해당 테이블용 추출 경로 지정 (DB 서버 Local 디스크 또는 High-speed SAN/NFS)
            String metaFile = "/data/export/" + tableName + "_meta.dat";
            String blobFile = "/data/export/" + tableName + "_blob.bin";

            stmt.execute("SET TEMPORARY OPTION Temp_Extract_Name1 = '" + metaFile + "'");
            stmt.execute("SET TEMPORARY OPTION Temp_Extract_Name2 = '" + blobFile + "'");
            stmt.execute("SET TEMPORARY OPTION Temp_Extract_Binary = 'ON'");
            stmt.execute("SET TEMPORARY OPTION Temp_Extract_Size1 = '21474836480'"); // 20GB 분할

            // 2. Query 실행 -> Sybase IQ 엔진이 DB 서버 디스크에 직접 대량 파일 생성
            System.out.println("Start Unload Table: " + tableName);
            stmt.executeQuery("SELECT * FROM " + tableName);
            System.out.println("Complete Unload Table: " + tableName);

            // 3. Reset
            stmt.execute("SET TEMPORARY OPTION Temp_Extract_Name1 = ''");
            stmt.execute("SET TEMPORARY OPTION Temp_Extract_Name2 = ''");

        } catch (Exception e) {
            System.err.println("Error Unloading Table " + tableName + ": " + e.getMessage());
        }
    }

    private static String[] getTableListFromDB() {
        // 13,000개 테이블 정보 조회 메타 로직
        return new String[]{"TABLE_0001", "TABLE_0002", "TABLE_0003"};
    }
}
```

-------


현재 구상하신 **`SybaseIQServerSideOrchestrator` 방향 자체는 맞습니다.**
특히 **Java가 250TB를 직접 읽어서 처리하지 않고, AS-IS Sybase IQ의 서버 측 UNLOAD와 TO-BE Sybase IQ의 서버 측 LOAD를 제어하는 방식**이 적절합니다.

다만 현재 코드 그대로 13,000개 / 250TB를 돌리는 것은 권장하지 않습니다. 핵심은 **"테이블마다 동일하게 8개씩 병렬 처리"가 아니라, 테이블의 크기·파티션·LOB/BINARY·행 수·I/O 특성에 따라 작업을 분류하고 동적으로 병렬도를 조절하는 것**입니다.

# 1. 전체적으로 권장하는 구조

제가 권장하는 구조는 다음과 같습니다.

```text
                         ┌─────────────────────────┐
                         │          GODIS          │
                         │ Batch Group / Job       │
                         │ Schedule / Common Code  │
                         └────────────┬────────────┘
                                      │ Shell
                                      ▼
                 ┌──────────────────────────────────┐
                 │ Sybase IQ Migration Orchestrator  │
                 │          Java / Spring            │
                 └──────────────┬───────────────────┘
                                │
              ┌─────────────────┼──────────────────┐
              │                 │                  │
              ▼                 ▼                  ▼
       Metadata Manager   Work Scheduler     Validation Manager
              │                 │                  │
              └────────────┬────┴──────────────────┘
                           │
             ┌─────────────┴─────────────┐
             │                           │
             ▼                           ▼
      AS-IS IQ 16.0                 TO-BE IQ 16.2
       HP-UX                          Linux
             │                           │
             │ UNLOAD                    │ LOAD TABLE
             ▼                           ▲
        ┌─────────────────────────────────────┐
        │       Shared Volume 50TB            │
        │                                     │
        │  /migration/                        │
        │    ├── READY                        │
        │    ├── RUNNING                      │
        │    ├── DONE                         │
        │    └── ERROR                        │
        └─────────────────────────────────────┘
```

핵심은 Java가 **데이터 이동 프로그램**이 아니라 **Migration Orchestrator** 역할을 하는 것입니다.

즉,

```text
Java
  ↓
UNLOAD SQL 생성/실행
  ↓
AS-IS IQ가 파일 생성
  ↓
공유볼륨
  ↓
LOAD TABLE SQL 생성/실행
  ↓
TO-BE IQ가 파일 읽음
  ↓
검증
```

구조가 좋습니다.

SAP IQ 문서에서도 서버 측 파일 경로는 데이터베이스 서버 기준으로 처리되며, 내부적인 UNLOAD/LOAD 방식이 외부 INPUT/OUTPUT 방식보다 상당한 성능 이점을 가질 수 있다고 설명합니다. ([SAP 도움말 포털][1])

# 2. 현재 코드에서 가장 먼저 수정해야 할 부분

현재 코드의 가장 큰 문제는 이것입니다.

```java
int maxParallelThreads = 8;

for (String tableName : tableList) {
    executor.submit(() -> {
        executeServerSideUnload(tableName);
    });
}
```

13,000개 테이블을 전부 동일한 작업으로 보는 것입니다.

실제 데이터가

```text
TABLE001       1 MB
TABLE002      10 MB
TABLE003     500 MB
...
TABLE10000   200 GB
TABLE11000     5 TB
```

이라면 문제가 심각합니다.

8개 병렬로 실행하면

```text
1MB
10MB
500MB
20GB
100GB
500GB
1TB
2TB
```

가 동시에 수행될 수 있습니다.

그러면 작은 테이블 몇 개 때문에 병렬도가 낭비되거나, 반대로 대형 테이블 8개가 동시에 돌면서 **AS-IS IQ I/O와 공유볼륨 I/O가 병목**이 될 수 있습니다.

따라서 **Size Class 기반 Scheduler**가 필요합니다.

# 3. 13,000개 테이블을 먼저 분류하십시오

Migration 시작 전에 AS-IS에서 반드시 다음 Metadata를 수집하는 것을 권장합니다.

| 항목                 | 용도          |
| ------------------ | ----------- |
| TABLE_NAME         | 테이블 식별      |
| OWNER              | 소유자         |
| ROW_COUNT          | 데이터 건수      |
| DATA_SIZE          | 데이터 크기      |
| COLUMN_COUNT       | 컬럼 수        |
| BINARY_COUNT       | BINARY 컬럼 수 |
| LONG_BINARY_COUNT  | LOB 여부      |
| LONG_VARCHAR_COUNT | LOB 여부      |
| PARTITIONED        | 파티션 여부      |
| PARTITION_COUNT    | 파티션 수       |
| PRIMARY_KEY        | PK 여부       |
| INDEX_COUNT        | Index 수     |
| LAST_MODIFIED      | 데이터 변경 여부   |
| CHAR/VARCHAR 비중    | 문자열 데이터 특성  |
| NUMERIC 비중         | 숫자 데이터 특성   |
| DATE 비중            | 날짜 데이터 특성   |
| 예상 UNLOAD SIZE     | 공유볼륨 사용량    |
| 예상 LOAD TIME       | 작업 시간       |

특히 사용자 프로젝트에서는 **BINARY 컬럼이 존재하는 테이블**을 별도 관리하는 것이 중요합니다.

SAP IQ는 BINARY 형식의 빠른 Load를 지원하며, `FORMAT BINARY` 및 BINARY column specification을 사용할 수 있습니다. ([SAP 도움말 포털][2])

또한 LONG BINARY/LONG VARCHAR는 일반 데이터와 달리 별도의 LOB 파일 처리가 필요할 수 있습니다. SAP IQ의 BFILE 기능은 서버에서 개별 LONG BINARY/LONG VARCHAR cell을 별도 OS 파일로 추출할 수 있습니다. ([SAP 도움말 포털][3])

# 4. 테이블을 5개 정도의 Class로 나누는 것을 추천합니다

예를 들어 초기 기준은 다음처럼 잡을 수 있습니다.

| Class |       데이터 크기 | 권장 처리 |
| ----- | -----------: | ----- |
| XS    |      < 100MB | 고병렬   |
| S     |  100MB ~ 1GB | 고병렬   |
| M     |   1GB ~ 10GB | 중병렬   |
| L     | 10GB ~ 100GB | 저병렬   |
| XL    |      > 100GB | 전용 처리 |

그리고 250TB 전체를 단순히

```text
8 threads
```

로 처리하지 않고,

```text
XS/S : 16~32
M    : 8~16
L    : 2~4
XL   : 1~2
```

처럼 **Class별 동시 실행량을 다르게** 합니다.

단, 위 숫자는 실제 운영값이 아니라 **튜닝 시작점**입니다.

최종 병렬도는 반드시

```text
AS-IS CPU
AS-IS IQ Main Store I/O
Shared Volume Write IOPS
Shared Volume Throughput
Network Throughput
TO-BE IQ CPU
TO-BE IQ I/O
TO-BE LOAD 성능
```

을 측정해서 결정해야 합니다.

SAP IQ의 Load 성능도 CPU core, underlying I/O bandwidth, physical memory 등에 크게 영향을 받습니다. 파티션 테이블 역시 partition type과 데이터 분포에 따라 성능 차이가 있습니다. ([SAP 도움말 포털][4])

# 5. 특히 50TB 공유볼륨 때문에 "동시 파일 용량"을 관리해야 합니다

이 부분이 현재 설계에서 빠져 있습니다.

전체 데이터는

```text
250TB
```

인데 공유볼륨은

```text
50TB
```

입니다.

따라서 절대로

```text
250TB / 50TB
```

관점으로 단순히 처리하면 안 됩니다.

**Shared Volume을 Queue Buffer로 사용하는 구조**로 설계해야 합니다.

예:

```text
                    50TB Shared Volume
                 ┌─────────────────────┐
AS-IS UNLOAD ───►│ READY               │
                 │                     │
                 │ RUNNING             │
                 │                     │
TO-BE LOAD  ◄────│ DONE                │
                 └─────────────────────┘
```

예를 들어

```text
최대 사용량 = 40TB
Reserved     = 10TB
```

처럼 운영 한도를 설정합니다.

그리고 Scheduler가

```text
현재 사용량
+ 예상 생성 파일 크기
> 40TB
```

이면 **UNLOAD를 더 이상 시작하지 않습니다.**

# 6. 매우 중요한 것은 "Unload와 Load를 동시에 수행"하는 것입니다

전체 프로세스를

```text
1. 13,000개 전부 UNLOAD
2. 13,000개 전부 LOAD
```

로 하면 안 됩니다.

권장 방식은 Pipeline입니다.

```text
                    Pipeline

Table A ── UNLOAD ──► READY ── LOAD ──► VALIDATE ──► DELETE

Table B ── UNLOAD ──► READY ── LOAD ──► VALIDATE ──► DELETE

Table C ── UNLOAD ──► READY ── LOAD ──► VALIDATE ──► DELETE

Table D ── UNLOAD ──► READY ── LOAD ──► VALIDATE ──► DELETE
```

예를 들어

```text
AS-IS
  │
  │  4 tables unload
  ▼
Shared Volume
  │
  │  4 tables load
  ▼
TO-BE
```

처럼 계속 흘려보냅니다.

이렇게 하면 50TB 볼륨을 **임시 저장소가 아니라 Streaming Buffer**처럼 사용할 수 있습니다.

# 7. 상태 관리가 반드시 필요합니다

현재 Java 프로그램은

```java
System.out.println("Start Unload");
...
System.out.println("Complete Unload");
```

정도입니다.

13,000개 / 250TB 프로젝트에서는 이것으로는 부족합니다.

MariaDB의 Migration Batch 관리 DB를 이미 사용하고 있으므로, 다음과 같은 상태를 관리하는 것을 권장합니다.

```text
MIG_TABLE_JOB
```

예:

| TABLE | STATUS | UNLOAD  | LOAD    | VALIDATE |  SIZE |
| ----- | ------ | ------- | ------- | -------- | ----: |
| A     | DONE   | OK      | OK      | OK       |   2GB |
| B     | LOAD   | OK      | RUNNING | WAIT     |  50GB |
| C     | UNLOAD | RUNNING | WAIT    | WAIT     | 100GB |
| D     | ERROR  | ERROR   | -       | -        |   1TB |

상태는 최소한

```text
READY
UNLOADING
UNLOADED
LOADING
LOADED
VALIDATING
DONE
ERROR
RETRY
```

정도로 두는 것이 좋습니다.

# 8. Retry 설계도 중요합니다

예를 들어

```text
TABLE_A
UNLOAD 성공
LOAD 실패
```

라고 해서 전체 Migration을 실패시키면 안 됩니다.

다음처럼 해야 합니다.

```text
TABLE_A

UNLOAD     SUCCESS
LOAD       FAILED
VALIDATE   WAIT

        ↓ Retry

LOAD       SUCCESS
VALIDATE   SUCCESS
DONE
```

그리고 Retry 횟수도

```text
retry_count = 0
retry_count = 1
retry_count = 2
retry_count = 3
```

처럼 관리합니다.

3회 실패하면

```text
ERROR
```

로 보내고 다음 테이블을 계속 진행하도록 합니다.

# 9. 파일도 하나의 "Migration Object"로 관리해야 합니다

현재 코드에서는

```java
String metaFile = "/data/export/" + tableName + "_meta.dat";
String blobFile = "/data/export/" + tableName + "_blob.bin";
```

인데, 실제 운영에서는 더 구조화하는 것을 권장합니다.

예:

```text
/migration/
  /JOB_20260914/
    /TABLE_A/
      /UNLOAD/
        data_001.dat
        data_002.dat
        blob/
      /LOAD/
      /CONTROL/
        manifest.json
        unload.sql
        load.sql
        result.json
```

특히 `manifest`를 두는 것이 좋습니다.

예:

```json
{
  "table": "TABLE_A",
  "rowCount": 123456789,
  "dataSize": 123456789012,
  "fileCount": 10,
  "binaryColumnCount": 2,
  "unloadStatus": "SUCCESS",
  "loadStatus": "SUCCESS"
}
```

그러면 장애가 발생했을 때

```text
DB 상태
+
파일 상태
+
Batch 상태
```

를 서로 맞출 수 있습니다.

# 10. 20GB 파일 분할은 고정값으로 두지 않는 것을 추천합니다

현재:

```java
stmt.execute(
    "SET TEMPORARY OPTION Temp_Extract_Size1 = '21474836480'"
);
```

20GB 고정입니다.

이것도 테이블 Class에 따라 달리 가져가는 것이 좋습니다.

예:

```text
XS/S
 → 1~5GB

M
 → 5~10GB

L
 → 10~20GB

XL
 → 20~50GB
```

다만 **실제 `Temp_Extract_*` 옵션의 정확한 의미와 지원 범위는 사용 중인 IQ 16.0 ESD/SP 레벨에서 반드시 확인하고 PoC에서 검증해야 합니다.**

특히 현재 예제의

```text
Temp_Extract_Name1
Temp_Extract_Name2
Temp_Extract_Binary
Temp_Extract_Size1
```

를 실제 IQ 16.0 환경에서 그대로 사용할 수 있는지 확인하는 것이 먼저입니다.

# 11. `SELECT * FROM table` 방식은 다시 검토해야 합니다

현재:

```java
stmt.executeQuery("SELECT * FROM " + tableName);
```

인데, 여기에는 몇 가지 문제가 있습니다.

첫째, Java JDBC가 결과를 받아 처리하는 것처럼 보입니다.

둘째, Migration metadata를 활용하지 않습니다.

셋째, BINARY/LOB 컬럼 처리 정책을 명확하게 분리하지 않았습니다.

따라서 실제 프로그램에서는

```text
Metadata
   ↓
Unload SQL Generator
   ↓
Table별 UNLOAD SQL
```

구조로 만드는 것을 추천합니다.

즉,

```java
String strUnloadSql =
    unloadSqlGenerator.generate(tableMetadata);
```

처럼 하는 것입니다.

# 12. BINARY/LOB 테이블은 별도 Queue로 분리하는 것이 좋습니다

특히 이 프로젝트에서는 중요합니다.

예:

```text
NORMAL_QUEUE

TABLE_A
TABLE_B
TABLE_C


BINARY_QUEUE

TABLE_X
TABLE_Y


LOB_QUEUE

TABLE_Z
TABLE_W
```

이렇게 나누는 것을 권장합니다.

왜냐하면

```text
일반 CHAR/NUMERIC/DATE
```

와

```text
LONG BINARY
LONG VARCHAR
BLOB
```

은 I/O 패턴이 다르기 때문입니다.

SAP IQ에서도 LOB 데이터는 별도 파일 구조를 사용하는 Load/Unload 기능을 제공합니다. ([SAP 도움말 포털][3])

# 13. 파티션 테이블은 더 적극적으로 활용할 수 있습니다

13,000개 중 대형 테이블이 많다면 **테이블 단위 병렬화만 생각하지 말고 Partition 단위 병렬화도 검토**해야 합니다.

예:

```text
TABLE_BIG
 ├─ 2020
 ├─ 2021
 ├─ 2022
 ├─ 2023
 ├─ 2024
 └─ 2025
```

를

```text
UNLOAD
 ├─ P2020
 ├─ P2021
 ├─ P2022
 ├─ P2023
 ├─ P2024
 └─ P2025
```

로 처리하는 것입니다.

SAP IQ는 range/hash/hash-range partitioned table에 대해 parallel bulk load를 지원합니다. 특히 range partition은 데이터가 partition 순서로 그룹화되어 있을 때 좋은 성능을 얻을 수 있습니다. ([SAP 도움말 포털][4])

따라서

```text
100GB table 1개
```

를 무조건

```text
1 Worker
```

로 보는 것보다

```text
100GB
 ├─ 20GB
 ├─ 20GB
 ├─ 20GB
 ├─ 20GB
 └─ 20GB
```

처럼 partition 구조를 활용할 수 있는지 검토해야 합니다.

# 14. 그러나 "무조건 Partition 병렬화"도 아닙니다

중요합니다.

예를 들어

```text
10TB Table
```

을

```text
8 Partition
×
8 Worker
```

로 돌린다고 해서 8배 빨라지는 것은 아닙니다.

오히려

```text

       ↓
     100%
       ↓
Shared Volume I/O
       ↓
     100%
       ↓
TO-BE IQ I/O
```

가 되어 전체 처리량이 떨어질 수 있습니다.

따라서 **Concurrency를 CPU 기준이 아니라 End-to-End Throughput 기준으로 결정해야 합니다.**

ASIS_IO       : 100

TABLE A
  ASIS_IO   5

현재 Resource

# 16. 더 중요한 것은 "Back Pressure"입니다

예를 들어

```text
UNLOAD
  ↓
Shared Volume
  ↓
LOAD
```

에서

```text
UNLOAD = 5 TB/hour
LOAD   = 2 TB/hour
```

이면 Shared Volume이 계속 증가합니다.

```text
10TB
15TB
20TB
30TB
40TB
...
```

그러면 50TB가 금방 찹니다.

따라서 Scheduler는

```text
Shared Volume Usage
```

를 지속적으로 보고

```text
< 60%
```

이면 UNLOAD 증가

```text
60~80%
```

이면 균형

```text
80~90%
```

이면 UNLOAD 감소

```text
> 90%
```

이면 UNLOAD STOP

같은 **Back Pressure**가 필요합니다.

이것이 50TB 공유볼륨을 사용하는 이번 프로젝트에서 상당히 중요한 설계 포인트입니다.

# 30. 결론

현재 생각하신 **`SybaseIQServerSideOrchestrator`는 방향이 좋습니다.** 특히 250TB를 Java가 직접 처리하지 않고 **Sybase IQ의 서버 측 Bulk UNLOAD/LOAD를 이용하는 것**은 유지하는 것을 권장합니다. SAP IQ 자체도 대량 데이터를 위한 `LOAD TABLE`과 binary load를 제공하며, 내부적인 서버 측 방식은 성능상 유리할 수 있습니다. ([SAP 도움말 포털][2])

다만 현재의

```java
newFixedThreadPool(8)
```

중심 설계는 **13,000개 / 250TB / 공유볼륨 50TB 규모에는 부족합니다.**

제가 권장하는 최종 개념은:

> **Metadata-driven + Size-aware + Resource-aware + Pipeline + Back-pressure + Retry + Validation**

입니다.

특히 이번 환경에서는 **"몇 개 Thread를 돌릴 것인가?"보다 "AS-IS → 50TB 공유볼륨 → TO-BE 전체 파이프라인의 처리량을 어떻게 최대로 유지할 것인가?"**가 핵심입니다.

그리고 파티션 테이블은 IQ가 병렬 Bulk Load를 지원하므로 대형 테이블의 경우 **Table-level parallelism과 Partition-level parallelism을 별도로 검토**하는 것이 좋습니다. ([SAP 도움말 포털][4])

### 다음 단계로 권장

이 프로젝트라면 다음 단계에서 바로 **실행 가능한 이관 아키텍처와 Scheduler 설계**까지 구체화하는 것이 좋습니다. 특히 다음 4개를 설계하면 실제 개발에 들어갈 수 있습니다.

1. **13,000개 테이블을 자동으로 XS/S/M/L/XL + NORMAL/BINARY/LOB/PARTITION 유형으로 분류하는 Metadata SQL**
2. **MariaDB `migration_job` 테이블 설계 및 상태 머신**
3. **`SybaseIQServerSideOrchestrator`를 Spring 기반으로 재작성한 실제 Java 클래스 구조**
4. **50TB 공유볼륨을 기준으로 UNLOAD/LOAD 동시성을 자동 조절하는 Resource-aware Scheduler 알고리즘**

이 4가지를 하나의 설계로 묶으면, 현재 구상하신 단순 Thread Pool 방식에서 **250TB 실운영용 Migration Orchestrator**로 발전시킬 수 있습니다.
