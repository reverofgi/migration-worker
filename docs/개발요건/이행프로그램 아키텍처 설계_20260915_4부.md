**현재 요구사항이라면 Pure Java 프로젝트가 더 적합합니다.**
제가 앞서 Spring Boot를 언급한 것은 확장성을 고려한 선택지였지만, 지금 설명해주신 **GODIS → Shell → Java Worker → Sybase IQ** 구조에서는 Spring Boot가 필수적이지 않습니다.

### 왜 Pure Java가 적합한가

현재 Worker의 역할은 매우 단순합니다.

```text
GODIS
  │
  │ Shell 실행
  ▼
MigrationWorkerApplication.main()
  │
  ├─ 파라미터 검증
  ├─ AS-IS JDBC 연결
  ├─ Sybase IQ UNLOAD SQL 실행
  │
  └─ TO-BE JDBC 연결
       └─ Sybase IQ LOAD TABLE SQL 실행
```

즉 Java가 담당하는 것은:

* Command Line Parameter 처리
* JDBC Connection 생성
* Sybase IQ SQL 실행
* Metadata 조회
* 파일/Manifest 상태 확인
* 로그 기록
* 검증 결과 저장
* Exit Code 반환

정도입니다.

**HTTP 서버, REST API, DI Container, Web Server, Spring Batch, Scheduler가 필요하지 않습니다.**

## 1. 특히 GODIS가 이미 배치 프레임워크를 가지고 있습니다

이 부분이 결정적입니다.

현재 구조가:

```text
GODIS
 ├─ Batch Group
 ├─ Batch Job
 ├─ Schedule
 ├─ 공통코드
 └─ 실행조건
       │
       ▼
     Shell
       │
       ▼
   Java Worker
```

이므로 Java Worker가 다시

```text
Spring Boot
 ├─ Scheduler
 ├─ Job
 ├─ Thread Pool
 └─ Batch 관리
```

를 가지면 **책임이 중복됩니다.**

따라서 저는 다음과 같이 분리하는 것을 권장합니다.

| 기능          | 담당           |
| ----------- | ------------ |
| 배치 그룹       | GODIS        |
| 배치 스케줄      | GODIS        |
| 실행 순서       | GODIS        |
| 재실행         | GODIS        |
| 테이블별 파라미터   | GODIS        |
| Worker 실행   | Shell        |
| 데이터 Extract | AS-IS IQ     |
| 데이터 Load    | TO-BE IQ     |
| SQL 실행 제어   | Java         |
| 이관 검증       | Java + IQ    |
| 결과/상태       | Java → GODIS |

# 2. `main()`을 Entry Point로 사용하는 것이 맞습니다

예를 들어:

```java
public class MigrationWorkerApplication {

    public static void main(String[] args) {

        try {

            MigrationParameter parameter =
                MigrationParameter.from(args);

            MigrationWorker worker =
                new MigrationWorker();

            worker.execute(parameter);

            System.exit(0);

        } catch (Exception ex) {

            ex.printStackTrace();

            System.exit(1);
        }
    }
}
```

GODIS에서는:

```bash
java -jar sybase-iq-migration-worker.jar \
    --mode=UNLOAD \
    --job-id=MIG000001 \
    --table=DBA.TABLE_A \
    --condition="REG_DTM >= '20260101'" \
    --source-file="/migration/MIG000001/TABLE_A/data.dat"
```

이렇게 실행하면 됩니다.

이 구조가 **아주 자연스럽습니다.**

# 3. 오히려 Spring Boot를 넣으면 불필요한 것이 많아집니다

예를 들어 Spring Boot에서는:

```text
SpringApplication
ApplicationContext
Bean
Dependency Injection
Configuration
Auto Configuration
Logging
Lifecycle
```

등이 추가됩니다.

하지만 현재 Worker는 결국:

```java
Connection conn =
    DriverManager.getConnection(...);

Statement stmt =
    conn.createStatement();

stmt.execute(...);
```

가 핵심입니다.

따라서:

```text
Spring Boot
    ↓
Java Application
    ↓
JDBC
    ↓
Sybase IQ
```

보다

```text
Java Application
    ↓
JDBC
    ↓
Sybase IQ
```

가 단순하고 운영하기 쉽습니다.

특히 **13,000개 테이블 / 250TB 이관처럼 운영 안정성이 중요한 Migration Worker에서는 의존성을 최소화하는 것이 장점**입니다.

# 6. `ExecutorService`도 제거하는 것을 권장합니다

앞서 올려주신 코드의:

```java
ExecutorService executor =
    Executors.newFixedThreadPool(8);
```

도 **현재 구조에서는 제거하는 것이 좋습니다.**

왜냐하면 GODIS가 이미:

```text
Batch Group
    │
    ├── Worker 1
    ├── Worker 2
    ├── Worker 3
    ├── Worker 4
    └── ...
```

형태로 테이블별 작업을 병렬 실행할 수 있기 때문입니다.

예를 들어:

```text
GODIS
 ├─ MIG_GROUP_SMALL
 │    ├─ TABLE001
 │    ├─ TABLE002
 │    └─ TABLE003
 │
 ├─ MIG_GROUP_MEDIUM
 │    ├─ TABLE101
 │    └─ TABLE102
 │
 └─ MIG_GROUP_LARGE
      └─ TABLE1001
```

그리고 GODIS가 동시 실행 개수를:

```text
Small   : 16
Medium  : 8
Large   : 2
```

처럼 관리하는 것이 훨씬 좋습니다.

# 7. 대신 IQ 내부 Parallelism은 별도로 관리

다만 다음 두 가지는 구분해야 합니다.

```text
① GODIS Parallelism

GODIS
 ├─ Worker A
 ├─ Worker B
 ├─ Worker C
 └─ Worker D


② Sybase IQ 내부 Parallelism

Worker A
   │
   ▼
IQ Extract
   ├─ Thread 1
   ├─ Thread 2
   ├─ Thread 3
   └─ Thread 4
```

즉 Java의:

```java
ExecutorService
```

는 제거하되 IQ의:

```sql
TEMP_EXTRACT_MAX_PARALLEL_DEGREE
```

같은 **IQ 자체 병렬 처리 기능은 사용**할 수 있습니다.

이렇게 해야 GODIS에서 전체 이관량을 통제할 수 있습니다.

# 9. 그리고 중요한 설계 변경을 하나 권장합니다

현재 이름이:

```java
SybaseIQServerSideOrchestrator
```

인데, 저는 이 이름도 변경하는 것을 권장합니다.

왜냐하면 실제 프로그램은 "Orchestrator"라기보다는 **Worker**이기 때문입니다.

추천:

```text
MigrationWorkerApplication
        ↓
MigrationWorker
```

또는

```text
SybaseIQMigrationWorker
```

입니다.

**Orchestrator는 GODIS가 담당합니다.**

즉:

```text
GODIS
   = Orchestrator

Java
   = Worker

Sybase IQ
   = Data Processing Engine
```

이렇게 역할을 명확하게 나누는 것이 좋습니다.

### 결론적으로

**네, Pure Java가 맞습니다.**

이번 프로젝트에서는:

* ❌ Spring Boot
* ❌ Spring Batch
* ❌ REST API
* ❌ Java 내부 Scheduler
* ❌ Java 내부 대규모 Thread Pool
* ❌ Java를 통한 ResultSet 데이터 이동

을 기본적으로 배제하고,

* ✅ Java SE
* ✅ JDBC / jConnect
* ✅ `main()` Entry Point
* ✅ Command Line Parameter
* ✅ Sybase IQ `SELECT`/Extract
* ✅ Sybase IQ `LOAD TABLE`
* ✅ Metadata 조회
* ✅ 이관 검증
* ✅ 로그/상태 관리
* ✅ OS Exit Code

만으로 구성하는 것이 **현재 GODIS 중심의 이관 아키텍처에 가장 깔끔합니다.**

그리고 이 구조라면 **Java 자체는 매우 가볍게 유지하면서 13,000개 테이블의 특성별 Batch Group/Schedule은 GODIS에서 전문적으로 통제**할 수 있습니다.

다음 단계에서는 이 구조를 기준으로 **`MigrationWorkerApplication → MigrationWorker → UnloadWorker → LoadWorker → Validator` 전체를 실제 운영 가능한 Pure Java 프로젝트 형태로 재작성하고, GODIS가 넘겨주는 `tableId/tableName/extractCondition/jobId`와 MariaDB Metadata를 이용해 13,000개 테이블의 `LOAD TABLE` SQL을 자동 생성하도록 설계하는 것이 적절합니다.**
