네. 말씀하신 구조라면 앞서 답변에서 설명한 **"Java가 데이터 이동을 수행한다"는 관점으로 볼 필요가 없습니다.** 정확히는 다음 구조가 맞습니다.

> **GODIS → Shell → Java Orchestrator → Sybase IQ SQL 실행 → AS-IS Sybase IQ 엔진이 데이터 추출 및 파일 생성**

즉 **Java는 데이터를 JVM으로 가져오지 않고, Sybase IQ에 명령만 내리는 제어 프로그램**으로 설계하는 것이 가장 적절합니다.

그리고 이 전제를 기준으로 보면 현재 `executeServerSideUnload()`는 상당히 단순화할 수 있고, 몇 가지 중요한 부분은 수정해야 합니다.

# 2. `TEMP_EXTRACT_NAME1`을 사용하는 방식이라면 실제 파일 생성 주체는 IQ입니다

SAP IQ의 Extract Option 문서에 따르면 `TEMP_EXTRACT_NAME1`을 지정하면 `SELECT`의 결과가 일반 client interface로 반환되는 대신 지정된 디스크 파일로 직접 redirect됩니다. 그리고 `TEMP_EXTRACT_NAME1`의 경로는 IQ 서버가 접근할 수 있는 파일 시스템이어야 합니다. ([SAP 도움말 포털][1])

예를 들어 Java가 다음을 실행합니다.

```sql
SET TEMPORARY OPTION TEMP_EXTRACT_NAME1 =
    '/migration/TABLE_A/data.dat';

SET TEMPORARY OPTION TEMP_EXTRACT_BINARY = 'ON';

SELECT
    COL1,
    COL2,
    COL3
FROM DBA.TABLE_A
WHERE ...
;
```

여기서:

```text
Java
  │
  │ SQL 전송
  ▼
IQ
  │
  │ SELECT 수행
  ▼
IQ Engine
  │
  │ 데이터 읽기
  ▼
/migration/TABLE_A/data.dat
```

입니다.

즉 Java가:

```java
ResultSet rs = stmt.executeQuery(...);
while (rs.next()) {
    ...
}
```

하는 구조가 아닙니다.

**Java는 ResultSet의 데이터를 소비하면 안 됩니다.**

---

# 3. 따라서 현재 코드의 이 부분은 개념적으로 맞습니다

현재 코드:

```java
stmt.executeQuery("SELECT * FROM " + tableName);
```

여기서 중요한 것은 `executeQuery()`라는 메서드 자체가 아니라 **SELECT가 실행되는 순간 IQ의 Extract Option에 의해 결과가 파일로 redirect된다는 것**입니다.

다만 저는 다음과 같이 바꾸는 것을 권장합니다.

```java
stmt.executeUpdate(
    "SET TEMPORARY OPTION TEMP_EXTRACT_NAME1 = ..."
);

stmt.executeUpdate(
    "SET TEMPORARY OPTION TEMP_EXTRACT_BINARY = 'ON'"
);

stmt.executeQuery(
    "SELECT ... FROM ... WHERE ..."
);
```

그리고 ResultSet을 읽지 않습니다.

---

# 4. 그러나 현재 코드에는 매우 중요한 문제가 하나 있습니다

현재:

```java
String metaFile = "/data/export/" + tableName + "_meta.dat";
String blobFile = "/data/export/" + tableName + "_blob.bin";

stmt.execute("SET TEMPORARY OPTION Temp_Extract_Name1 = '" + metaFile + "'");
stmt.execute("SET TEMPORARY OPTION Temp_Extract_Name2 = '" + blobFile + "'");
```

이것은 **BINARY/LOB가 있는 모든 테이블을 동일하게 처리하는 방식으로 만들면 안 됩니다.**

왜냐하면 Extract Option에는 `TEMP_EXTRACT_NAME1`부터 `TEMP_EXTRACT_NAME8`까지 여러 출력 파일을 지정할 수 있고, 파일별 `TEMP_EXTRACT_SIZE<n>`도 지정할 수 있기 때문입니다. ([SAP 도움말 포털][1])

따라서 테이블 metadata를 기준으로 Extract Option을 구성해야 합니다.

# 5. 그리고 `20GB` 설정은 단위가 잘못될 가능성이 높습니다

현재:

```java
stmt.execute(
    "SET TEMPORARY OPTION Temp_Extract_Size1 = '21474836480'"
);
```

주석은:

```text
20GB
```

인데 SAP IQ 문서상 `TEMP_EXTRACT_SIZE<n>`은 **KB 단위**입니다. 예를 들어 1MB는 1024 KB입니다. ([SAP 도움말 포털][1])

따라서 20GB라면:

```text
20 × 1024 × 1024
= 20,971,520 KB
```

입니다.

즉 현재:

```text
21,474,836,480
```

을 넣으면 20GB가 아니라 엄청나게 큰 값이 됩니다.

이 부분은 **반드시 수정해야 합니다.**

예:

```java
private static final long EXTRACT_SIZE_20GB_KB =
        20L * 1024L * 1024L;
```

그리고:

```java
stmt.executeUpdate(
    "SET TEMPORARY OPTION TEMP_EXTRACT_SIZE1 = "
    + EXTRACT_SIZE_20GB_KB
);
```

처럼 해야 합니다.

---

# 6. 더 중요한 점: Java에서 20GB 파일을 "분할"하는 것이 아닙니다

이 부분도 명확하게 구분해야 합니다.

Java가:

```text
20GB 읽음
→ 파일 생성
→ 다음 20GB
```

하는 것이 아닙니다.

IQ Extract Engine이:

```text
SELECT
   │
   ├── file 1
   ├── file 2
   ├── file 3
   └── ...
```

형태로 처리합니다.

SAP IQ Extract Option은 파일 이름과 크기를 지정하여 SELECT 결과를 여러 파일로 추출할 수 있습니다. ([SAP 도움말 포털][2])

따라서 Java는:

```text
파일 분할 로직
X

파일 write 로직
X

byte counting
X

buffer
X

Java heap 관리
X
```

가 필요 없습니다.

이게 이번 구조의 큰 장점입니다.

---

# 7. 따라서 Java 프로그램의 역할을 극단적으로 단순화하는 것이 좋습니다

제가 권장하는 Java의 책임 범위는 다음입니다.

```text
① Parameter 수신
② Table/Column Metadata 확인
③ Extract SQL 생성
④ Extract Option 설정
⑤ SELECT 실행
⑥ 실행 결과/에러 확인
⑦ 파일 생성 상태 확인
⑧ Migration 결과 기록
```

반대로 하지 않아야 하는 것은:

```text
X ResultSet 데이터 처리
X Java 파일 write
X Java buffer
X Java compression
X Java binary conversion
X Java row-by-row processing
X Java data transformation
```

입니다.

# 10. 즉 GODIS가 Scheduler, Java는 Worker가 됩니다

```text
 └─ Scheduler
```

를 제안했지만, 현재 설명해 주신 구조라면 **그럴 필요가 없습니다.**

```text

```

가 더 적합합니다.

**GODIS가 Orchestrator이고 Java는 IQ Server-side Operation Executor인 구조**입니다.

# 12. 가장 중요한 수정: `executeQuery()`는 "실행 완료"를 의미합니다

현재:

```java
System.out.println("Start Unload Table: " + tableName);

stmt.executeQuery(
    "SELECT * FROM " + tableName
);

System.out.println("Complete Unload Table: " + tableName);
```

이 부분은 상당히 좋은 형태입니다.

왜냐하면 IQ 서버가 SELECT를 수행하면서 extract 파일을 생성하기 때문입니다.

즉:

```text
executeQuery()
```

호출

↓

```text
JDBC
   ↓
IQ Server
   ↓
Query execution
   ↓
Extract engine
   ↓
File write
```

가 완료된 후 Java가 반환을 받습니다.

따라서 Java는 데이터 처리량에 비례해서 메모리를 사용하는 프로그램이 아닙니다.

# 13. 다만 `executeQuery()`보다는 `execute()`를 권장합니다

이 작업의 목적은 ResultSet을 가져오는 것이 아니기 때문입니다.

따라서:

```java
stmt.executeQuery(sql);
```

보다는:

```java
stmt.execute(sql);
```

가 의도를 더 명확하게 나타냅니다.

예:

```java
boolean boolResult = stmt.execute(strExtractSql);
```

여기서 중요한 것은 반환된 ResultSet을 처리하는 것이 아니라 **SQL 실행이 정상적으로 완료되었는지**입니다.

# 14. 제가 권장하는 핵심 메서드

예를 들어 다음 정도가 적절합니다.

```java
private void executeServerSideUnload(
        String strTableName,
        String strExtractCondition,
        String strOutputFile) {

    String strSql = buildExtractSql(
        strTableName,
        strExtractCondition
    );

    try (
        Connection conn =
            DriverManager.getConnection(
                this.strDbUrl,
                this.strUser,
                this.strPassword
            );
        Statement stmt = conn.createStatement()
    ) {

        conn.setAutoCommit(true);

        // 1. Extract 설정
        setExtractOptions(
            stmt,
            strOutputFile
        );

        // 2. IQ Server에서 SELECT 실행
        System.out.println(
            "Start server-side extract : "
            + strTableName
        );

        stmt.execute(strSql);

        // 3. 실행 완료
        System.out.println(
            "Complete server-side extract : "
            + strTableName
        );

    } finally {
        // Connection 종료와 함께 TEMPORARY OPTION도
        // connection scope에서 종료되도록 구성
    }
}
```

이렇게 하면 Java 코드가 매우 작아집니다.

# 15. `TEMPORARY OPTION`은 Connection 단위로 관리하는 것이 중요합니다

SAP IQ 문서에서도 extract option은 **connection에 설정되는 옵션**이며, extract가 끝나면 `TEMP_EXTRACT_NAME1`을 빈 문자열로 설정하거나 연결을 끊어서 비활성화하도록 설명합니다. 또한 동일한 사용자 ID를 다른 사용자가 사용하면 extract 결과가 서로 영향을 받을 수 있으므로 unique user ID 사용을 권고합니다. ([SAP 도움말 포털][3])

따라서 현재처럼:

```java
try (Connection conn = ...)
```

으로 **작업별 Connection을 만들고**

```text
SET TEMPORARY OPTION
       ↓
SELECT
       ↓
Connection close
```

하는 구조는 상당히 적절합니다.

특히 GODIS에서 여러 Java 작업을 동시에 실행할 경우에는 **각 작업의 Extract Option이 서로 섞이지 않도록 Connection scope를 분리**하는 것이 중요합니다.

---

# 16. 그래서 Connection Pool은 오히려 사용하지 않는 것을 추천합니다

이번 프로그램은 일반적인 Spring Web Application과 다릅니다.

일반적인:

```text
Connection Pool
 ├─ Connection 1
 ├─ Connection 2
 ├─ Connection 3
 └─ ...
```

보다는:

```text
GODIS Job
   ↓
Java Process
   ↓
Connection
   ↓
SET TEMPORARY OPTION
   ↓
SELECT
   ↓
close
```

가 더 안전합니다.

특히 Extract Option이 connection/session 상태이므로 **작업 하나가 하나의 명확한 DB session을 소유하도록 하는 것**이 좋습니다.

# 17. 테이블 조건도 Java에서 문자열 그대로 조립할 수는 있지만 검증 계층을 두는 것이 좋습니다

GODIS에서:

```text
TABLE_NAME
EXTRACT_CONDITION
```

을 전달한다고 하셨으므로 예를 들어:

```text
TABLE_NAME = DBA.CUSTOMER

EXTRACT_CONDITION =
REG_DATE >= '20260101'
AND REG_DATE < '20260201'
```

이면 Java는:

```sql
SELECT *
FROM DBA.CUSTOMER
WHERE REG_DATE >= '20260101'
  AND REG_DATE < '20260201'
```

을 생성합니다.

여기서 `TABLE_NAME`과 `EXTRACT_CONDITION`은 일반적인 JDBC PreparedStatement의 `?` 파라미터와는 성격이 다릅니다.

따라서:

```text
TABLE_NAME
→ Metadata에서 존재 여부 확인

CONDITION
→ GODIS에서 정의된 Migration 조건을 그대로 전달
```

하는 식으로 **입력 책임을 명확하게** 하는 것이 좋습니다.

# 18. `SELECT *`도 최종적으로는 Metadata 기반으로 바꾸는 것을 추천합니다

예를 들어:

```sql
SELECT *
FROM DBA.CUSTOMER
WHERE ...
```

도 가능하지만, Migration 프로그램에서는 다음 구조가 더 안전합니다.

```text
Metadata
   │
   ├── Column 1
   ├── Column 2
   ├── Column 3
   └── Binary Column
           │
           ▼
Extract SQL Builder
           │
           ▼
SELECT COL1,COL2,COL3,...
```

특히 BINARY/LOB 테이블은 컬럼 처리 방식이 다를 수 있습니다.

---

# 19. BINARY/LOB는 일반 파일 하나로 생각하면 안 됩니다

SAP IQ의 `LOAD TABLE`은 ASCII/BINARY 파일을 서버에서 직접 읽을 수 있고, 여러 파일을 지정할 수 있습니다. 서버-side `FROM`/`USING FILE`의 경로는 **database server 기준**입니다. 또한 여러 파일을 이용한 Load는 병렬 처리될 수 있습니다. ([SAP 도움말 포털][4])

LOB의 경우에는 `BINARY FILE(...)`, `ASCII FILE(...)` 형태의 extended LOAD 구문도 존재합니다. ([SAP 도움말 포털][5])

따라서 이번 프로젝트에서는:

```text
NORMAL TABLE
BINARY TABLE
LOB TABLE
PARTITION TABLE
```

별로 Extract/Load SQL Generator를 분리하는 것이 좋습니다.

---

# 20. 향후 TO-BE Load도 동일한 철학으로 만들면 됩니다

AS-IS:

```text
Java
 ↓
SET TEMPORARY OPTION
 ↓
SELECT
 ↓
IQ Engine
 ↓
Shared Volume
```

TO-BE:

```text
Java
 ↓
LOAD TABLE
 ↓
TO-BE IQ Engine
 ↓
Shared Volume read
 ↓
TO-BE table
```

입니다.

예를 들어:

```sql
LOAD TABLE DBA.CUSTOMER
(
    COL1,
    COL2,
    COL3
)
FROM '/migration/CUSTOMER/data_001.dat'
FORMAT BINARY;
```

이 경우에도 Java가 파일을 읽는 것이 아닙니다.

**TO-BE IQ Server가 Shared Volume의 파일을 직접 읽습니다.**

SAP IQ 문서도 server-side `LOAD TABLE ... FROM`/`USING FILE`은 database server가 파일을 읽는 방식이라고 명확하게 설명합니다. ([SAP 도움말 포털][4])

```text
                      ▼
             Java Executor

   IQ Extract Engine              │
          │                       │
          ▼                       │
       ┌──────────────────────────────┐
       │       Shared Volume          │
       │            50TB              │
       └──────────────────────────────┘
```

**Java는 이 그림에서 가운데의 "제어선"일 뿐이고 데이터선에 들어가지 않습니다.**

이 구조를 유지하는 것을 강하게 추천합니다.

# 22. 그렇다면 Java를 어떻게 최적화해야 하는가?

이번 요구사항에서는 **성능 최적화의 방향이 일반적인 Java 프로그램과 다릅니다.**

Java의 목표:

```text
CPU 사용량 ↓
Heap 사용량 ↓
File I/O ↓
Network Data Transfer ↓
Connection 안정성 ↑
SQL 실행 제어 ↑
Error Detection ↑
```

입니다.

데이터 처리량을 Java에서 높이는 것이 목표가 아닙니다.

실제 성능을 좌우하는 것은:

```text
AS-IS IQ
     ↓
SELECT / Extract
     ↓
AS-IS Disk I/O
     ↓
Shared Volume
     ↓
TO-BE Disk I/O
     ↓
TO-BE IQ Load
```

입니다.

# 23. 그래서 최적화된 Java는 오히려 다음 정도면 충분합니다

```java
public class SybaseIQServerSideUnload {

    private final String strDbUrl;
    private final String strUser;
    private final String strPassword;

    public SybaseIQServerSideUnload(
            String strDbUrl,
            String strUser,
            String strPassword) {

        this.strDbUrl = strDbUrl;
        this.strUser = strUser;
        this.strPassword = strPassword;
    }

    public void execute(
            String strTableName,
            String strExtractCondition,
            String strOutputFile) throws Exception {

        String strSql =
            buildSelectSql(
                strTableName,
                strExtractCondition
            );

        try (
            Connection conn =
                DriverManager.getConnection(
                    this.strDbUrl,
                    this.strUser,
                    this.strPassword
                );
            Statement stmt =
                conn.createStatement()
        ) {

            // Extract Option
            setExtractOption(
                stmt,
                strOutputFile
            );

            System.out.println(
                "START : " + strTableName
            );

            // 중요:
            // Java가 ResultSet 데이터를 읽지 않는다.
            // SELECT 결과는 IQ Extract Engine이 파일로 출력한다.
            stmt.execute(strSql);

            System.out.println(
                "END : " + strTableName
            );
        }
    }

    private void setExtractOption(
            Statement stmt,
            String strOutputFile)
            throws Exception {

        stmt.executeUpdate(
            "SET TEMPORARY OPTION " +
            "TEMP_EXTRACT_NAME1 = '" +
            escapeSqlLiteral(strOutputFile) +
            "'"
        );

        stmt.executeUpdate(
            "SET TEMPORARY OPTION " +
            "TEMP_EXTRACT_BINARY = 'ON'"
        );

        stmt.executeUpdate(
            "SET TEMPORARY OPTION " +
            "TEMP_EXTRACT_NAME2 = ''"
        );
    }

    private String buildSelectSql(
            String strTableName,
            String strExtractCondition) {

        StringBuilder strBuilder =
            new StringBuilder();

        strBuilder.append("SELECT * ");
        strBuilder.append("FROM ");
        strBuilder.append(strTableName);

        if (strExtractCondition != null
                && !strExtractCondition.trim().isEmpty()) {

            strBuilder.append(" WHERE ");
            strBuilder.append(strExtractCondition);
        }

        return strBuilder.toString();
    }

    private String escapeSqlLiteral(
            String strValue) {

        return strValue.replace("'", "''");
    }
}
```

이 정도가 **"Java는 관장만 하고 IQ가 데이터를 처리한다"는 철학에 맞는 코드**입니다.

# 24. 다만 저는 한 가지 더 개선하겠습니다

`TEMP_EXTRACT_NAME1` 설정과 SELECT 실행을 별도의 SQL로 보내기보다는 **한 Connection에서 반드시 다음 순서를 보장**합니다.

```text
Connection OPEN
      ↓
TEMP_EXTRACT 옵션 설정
      ↓
SELECT
      ↓
Execution 완료
      ↓
TEMP_EXTRACT_NAME1 = ''
      ↓
Connection CLOSE
```

즉:

```java
try (Connection conn = ...;
     Statement stmt = ...) {

    configureExtract(stmt);

    executeExtract(stmt);

    clearExtractOptions(stmt);
}
```

로 구성합니다.

`TEMP_EXTRACT_NAME1`은 빈 문자열이면 extraction이 비활성화됩니다. SAP IQ 문서도 SELECT 이후 이를 빈 문자열로 재설정하도록 안내합니다. ([SAP 도움말 포털][1])

# 25. 그런데 `finally`에서 Clear하는 것보다 Connection Close에 의존하는 것도 가능합니다

`TEMPORARY OPTION`이라는 특성상 Connection 종료와 함께 session이 사라집니다.

그래도 운영 안정성을 위해 저는 명시적으로:

```java
clearExtractOptions(stmt);
```

하고 Connection을 닫는 것을 권장합니다.

그러면 로그를 볼 때도:

```text
SET EXTRACT
SELECT
CLEAR EXTRACT
CLOSE CONNECTION
```

이라는 명확한 lifecycle이 생깁니다.

# 26. 최종적으로 GODIS와 Java의 책임을 이렇게 나누는 것을 권장합니다

| 기능                       | GODIS | Java | Sybase IQ |
| ------------------------ | ----: | ---: | --------: |
| Batch Group              |     ◎ |      |           |
| Schedule                 |     ◎ |      |           |
| Table 선정                 |     ◎ |      |           |
| Extract Condition        |     ◎ |      |           |
| 동시 Job 수                 |     ◎ |      |           |
| Job Parameter            |     ◎ |    ○ |           |
| DB Connection            |       |    ◎ |           |
| Extract SQL 생성           |       |    ◎ |           |
| SELECT 실행                |       |    ◎ |         ◎ |
| 실제 데이터 Scan              |       |      |         ◎ |
| 파일 생성                    |       |      |         ◎ |
| 파일 Write                 |       |      |         ◎ |
| Shared Volume Read/Write |       |      |         ◎ |

| 데이터 Validation SQL       |       |    ◎ |         ◎ |

여기서 핵심은 **Java의 ◎가 "데이터를 처리한다"는 뜻이 아니라 "명령을 실행한다"는 뜻**입니다.

# 28. 한 가지 더: `maxParallelThreads = 8`도 Java에서 제거할 가능성이 높습니다

이것이 이번 질문에서 중요한 결론입니다.

GODIS가 이미:

```text
Batch Group
 ├─ Job 1
 ├─ Job 2
 ├─ Job 3
 ├─ ...
```

을 관리한다면 Java 안에서 다시:

```java
ExecutorService executor =
    Executors.newFixedThreadPool(8);
```

를 사용할 필요가 없습니다.

오히려:

```text
GODIS
  │
  ├── Java #1 ── TABLE A
  ├── Java #2 ── TABLE B
  ├── Java #3 ── TABLE C
  └── Java #4 ── TABLE D
```

가 이미 **프로세스 레벨 병렬 처리**입니다.

즉:

> **GODIS가 병렬도를 제어하고 Java는 단일 Table Migration Worker로 만드는 것**

을 저는 더 강하게 추천합니다.

# 29. 최종 권장 형태

따라서 이번 프로젝트에서 제가 권장하는 것은 다음입니다.

```text
                 GODIS
                  │
        ┌─────────┼─────────┐
        │         │         │
     Batch 1   Batch 2   Batch 3
        │         │         │
        ▼         ▼         ▼
     Shell      Shell      Shell
        │         │         │
        ▼         ▼         ▼
     Java       Java       Java
        │         │         │
        ▼         ▼         ▼
    AS-IS IQ   AS-IS IQ   AS-IS IQ
        │         │         │
        └─────────┼─────────┘
                  ▼
             50TB Volume
                  │
                  ▼
               TO-BE IQ
```

그리고 각 Java 프로세스는:

```text
START
 ↓
Parameter Parse
 ↓
Connection Open
 ↓
Set TEMP_EXTRACT options
 ↓
SELECT ... WHERE [GODIS condition]
 ↓
IQ가 실제 데이터 추출
 ↓
IQ가 파일 생성
 ↓
SELECT 완료
 ↓
Extract Option Clear
 ↓
Connection Close
 ↓
EXIT CODE 반환
```

입니다.

**Java Heap에는 250TB 데이터가 들어오지 않습니다.**

## 결론

질문하신 부분에 대해서는 명확하게 **"예"**입니다.

현재 구상하신 `TEMP_EXTRACT_NAME1` 기반 방식이 실제 IQ 16.0에서 지원되는 Extract 방식이라면,

> **Shell이 Java를 실행 → Java가 JDBC로 IQ에 명령 → IQ Engine이 AS-IS 데이터를 직접 읽고 Shared Volume에 파일 생성 → Java는 완료 여부만 확인하고 종료**

라는 구조가 맞습니다. SAP IQ의 Extract Option은 SELECT 결과를 직접 디스크 파일로 redirect하는 기능입니다. ([SAP 도움말 포털][1])

따라서 이번 프로젝트에서는 **Java를 더 복잡하게 만들수록 좋은 것이 아닙니다.** 오히려 `ExecutorService`, Java 파일 처리, ResultSet 처리 등을 제거하고 **"GODIS가 Orchestration, Java가 Command Executor, IQ가 Data Engine"**이라는 3계층으로 명확히 분리하는 것이 가장 좋습니다.

그리고 현재 코드에서 반드시 수정할 핵심은 **① `Temp_Extract_Size1`의 KB 단위 문제, ② `SELECT *`를 metadata 기반 SQL로 발전, ③ BINARY/LOB 별도 처리, ④ Job별 독립 Connection, ⑤ Java 내부 Thread Pool 제거, ⑥ GODIS parameter 기반 실행**입니다.

특히 `TEMP_EXTRACT_SIZE1 = 21474836480`은 **20GB를 의미하는 값이 아니므로 반드시 수정해야 합니다.** IQ 문서상 단위가 KB입니다. ([SAP 도움말 포털][1])

원하시면 다음 단계에서는 이 구조를 기준으로 **실제 운영에 바로 적용할 수 있는 `SybaseIQServerSideUnload.java` 전체 소스**를 `GODIS → Shell → Java parameter → IQ 16.0 Server-side Extract → Shared Volume` 흐름에 맞춰 작성하고, **일반 테이블 / BINARY 테이블 / LONG BINARY·LOB 테이블 / 추출조건 / 파일분할 / 종료코드 / 로그 / 예외처리**까지 포함한 형태로 구체화할 수 있습니다.
